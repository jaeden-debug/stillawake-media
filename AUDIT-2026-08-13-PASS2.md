**C. `x-default` — correction to my own audit.**
Pass 1 said "0 x-default anywhere." **That was wrong.** It was already correct on **47 pages** — I had parsed only the sitemap, which lacked it. The pages were right; the sitemap now matches.

Implementation: `x-default` points at the **EN URL of each pair**, not at `/global`. `x-default` names the default *within a cluster* — sending someone who requested `/shopify-development` to a page about remote engagement would be a redirect, not a language fallback. Pages with no FR counterpart get no alternates at all, which is correct; `x-default` is meaningless outside a cluster. Reciprocity re-verified: **0 broken.**

**D. `/fr/services` — deliberately NOT built.**
The French nav links all seven service pages directly (Création Web, SEO, Shopify, Maintenance, Référencement IA, Logiciels, Image de marque). There is no dead end. `/services` EN draws 7 impressions at position 7.6 — all branded. French is also the hardest, smallest market in the demand data. **E. Stale `lastmod` — 54 corrected, none invented.**
Dates were derived from each file's actual last commit via `git log`, not fabricated. The homepage claimed 2026-05-25 while its source last changed 2026-08-13.
⚠️ These remain **hand-maintained** by design (the file's own comment explains why: deriving from `new Date()` re-stamped every route on every deploy). They will drift again. Deriving from git at build time is unreliable on Vercel's shallow clones.

**F. `llms.txt` in `robots.txt` — deliberately NOT added.**
There is no registered `robots.txt` directive for `llms.txt`, and no crawler documents consuming one. An unrecognised line is ignored at best and a parse risk at worst. The convention is a well-known path at the domain root, which you already serve correctly. **No change — this was cargo-culting, not a fix.**

## 5. CONVERSION TRACKING — DESIGNED, NOT YET IMPLEMENTED

The journey is `stillawakemedia.com → CTA → stillawake.studio/start → lead row in Supabase`.

**Recommended event model:**

| Event | Type | Where | Why |
|---|---|---|---|
| `generate_lead` | **PRIMARY** | Studio, on successful onboarding submit | The only event that equals a real lead. This is the sole Ads conversion action. |
| `contact_form_submit` | **PRIMARY** | .com contact form success | A real enquiry. |
| `start_onboarding` | Secondary | Studio `/start` first question answered | Measures whether the hand-off works. |
| `cta_click_start` | Secondary | Any `stillawake.studio/start` link | Attributes which page drives intent. |
| `pricing_cta_click` | Secondary | `/pricing` | Diagnostic only. |

**Deliberately not conversions:** page views, scroll depth, `/pricing` visits. Marking engagement as conversion is what teaches Smart Bidding to buy browsers.

**Cross-domain — the important part.** `.com` and `stillawake.studio` are different domains. Without configuration, GA4 starts a new session at the hand-off and attributes the lead to `stillawakemedia.com` as a *referral*, destroying the original source. Required:
1. Add both domains to the GA4 property's cross-domain **Configure tag settings → Configure your domains**
2. Add `stillawakemedia.com` and `stillawake.studio` to the **unwanted referrals** list
3. Install the same GA4 tag on the Studio (it is not there today)

**Not implemented in this pass** — it needs GA4 admin UI changes only you can make, and installing a tag on the Studio is a second-repo change I did not want to bundle into a privacy commit. Flagged as a manual action in §17.

## 6. PRIVACY / CONSENT — WAS THE MOST SERIOUS FINDING, NOW FIXED

**What I found (verified in-browser, production):**
- GA4 and Clarity both started on page load with **no consent mechanism anywhere**
- Four cookies set before any interaction: `_ga`, `_ga_KE1CWNHY0S`, `_clck`, `_clsk`
- **Clarity session replay began automatically** — the most invasive thing on the site
- `gtag('consent', ...)` calls: **zero**. Consent Mode was not implemented.
- **No privacy policy existed.** `/privacy`, `/privacy-policy`, `/fr/confidentialite`, `/terms`, `/cookies`, `/legal` — all **404**. No footer link.
- Ahrefs analytics: **verified genuinely cookieless** — sets no cookie and no identifier

The site meanwhile publishes `/fr/articles/loi-25-cookies-consentement` — an article about Law 25 cookie consent.

**What this exposed you to:** Québec Law 25 requires consent for non-essential technology and has had administrative monetary penalties available since Sept 2023. GDPR/UK GDPR require prior consent for analytics cookies — and `/global` explicitly targets UK visitors. Session replay is treated as high-risk processing under both.

**What was implemented:**
- **Google Consent Mode v2**, all storage denied by default, emitted from a plain inline script placed as the first child of `<body>` — guaranteed to execute before `gtag.js`, so GA4's very first request already carries the denied signal
- **Clarity fully withheld** until explicit Accept — not merely consent-signalled
- **Ahrefs left ungated**, justified by the verified absence of cookies/identifiers
- **First-party banner, ~2KB**, no CMP vendor. A vendor bundle would outweigh everything it gates on a site with a 110–220 ms TTFB.
- **EN + FR**, Accept and Decline identical in size and weight, Decline not buried behind "manage preferences" — no dark patterns
- Choice persisted in `localStorage` with a timestamp (evidence of when consent was given, which Law 25 expects)
- `ad_storage` / `ad_user_data` / `ad_personalization` denied **permanently** — there are no ad tags to grant. If remarketing is ever added, that becomes a deliberate decision rather than an inherited default.

**Verified in a real browser, storage cleared between runs:**

| State | Cookies | Clarity | GA4 |
|---|---|---|---|
| No choice yet | **0** | **0 requests** | cookieless ping only |
| **Decline** | **0** | **0 requests** | cookieless ping only |
| **Accept** | 4 | tag + collect ✅ | full |
| Returning (accepted) | 4 | auto-loads | **1** page_view, no banner |

**A bug I introduced and caught here:** the first implementation fired `consent update` **52 times** on one page view — `useSyncExternalStore` was handed a snapshot function returning a fresh object each call, so React saw the store change on every render and looped. Fixed by returning the raw string (compared by value) and parsing in a memo. `tsc` and ESLint were both clean; only the browser caught it.

**Still outstanding:** the privacy policy is factually grounded in what actually runs, but it is legal text making commitments on your behalf. **Have it reviewed before relying on it.**
